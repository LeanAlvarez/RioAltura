# 007 — UI v2 y visualización de todos los datos

- **Estado:** lista
- **Rama:** feat/007-ui-v2
- **Depende de:** 003 (pronóstico), 005 (dashboard), 006 (mapa) — todas mergeadas
- **Puede ir en paralelo con:** nada (toca el layout completo del frontend)

## Objetivo

Que un vecino de Colón, sin conocimientos técnicos y con un celular en 3G, entienda en 5 segundos
cómo está el río, qué se espera y si tiene que preocuparse. Y que se aprovechen todos los datos que
ya tenemos guardados, que hoy se muestran a medias.

## Diagnóstico previo (medido, no supuesto)

Estado tomado el 2026-09-21 sobre `main` (commit `6c3966d`) con el stack real levantado: base
migrada, INA y Google backfilleados, API en `/health` respondiendo `{"status":"ok","db":"ok"}`.
Capturas en `img/007-antes-360.png` y `img/007-antes-1280.png`.

**Dos supuestos del pedido original no se verificaron, y la spec los corrige:**

1. **"El indicador 'API no disponible' aparece aunque la API responde" no se reproduce con la API
   real**: el indicador muestra "API en línea". El síntoma es real pero sólo en modo mocks, y su
   causa es otra: `fetchHealth` (`frontend/src/api.ts:29`) usa el `fetch` global en vez de
   `defaultFetch`, y `frontend/src/mocks/fetch.ts` no tiene handler para `/health`. Con
   `VITE_USE_MOCKS=true` el indicador siempre dice que la API está caída.
2. **La contradicción "hoy real 3,67 m vs pronóstico 1,4 a 3,4 m" es de los mocks, no de los datos
   reales.** Con datos reales de hoy: altura 4,29 m y pronóstico para hoy "entre 2,7 y 4,7 m" — el
   valor real cae dentro del rango. El sesgo real es +0,62 m, menor que el error p90 de la curva
   (1,1 m). Los mocks fabrican una altura de 3,67 m junto a caudales que no la sostienen.

El anclaje se implementa igual: 0,62 m de sesgo es visible y el mecanismo es correcto.

**Problemas reales encontrados, no reportados:**

3. **El primer "próximo día" es ayer.** La última emisión de Google es del 2026-09-20T23:45Z, y su
   `lead_dias = 0` cae en ese día. La lista arranca en "Dom 20": un día pasado presentado como
   pronóstico.
4. **El dato del INA llega con 17 h de atraso** y la tarjeta lo declara "dato desactualizado (más de
   6 h)" en su estado normal de operación.
5. **En desktop el panel del mapa tapa media ciudad**: ocupa una franja blanca de 20rem de arriba a
   abajo sobre el casco urbano.

**Problemas confirmados del pedido:** leyenda del gráfico con "--" (es la leyenda por defecto de
uPlot), eje X en formato `9/1` en vez de español, umbrales sin etiqueta, sin tooltip, mapa chico,
botones de escenarios cortados, layout de una sola columna de 720 px que desperdicia el ancho en
escritorio.

## Alcance

### Correcciones

- **C1 — Indicador de salud honesto.** `fetchHealth` usa `defaultFetch`; los mocks responden
  `/health`. El indicador sólo dice "API no disponible" cuando la API falla de verdad.
- **C2 — Anclaje del pronóstico a la altura real.** Ver "Diseño" abajo.
- **C3 — La lista de próximos días arranca hoy.** Se descartan los días con `fecha` anterior a hoy
  (zona `America/Argentina/Buenos_Aires`), no por `lead_dias`.

### Tarjetas y gráficos

- **T1 — Próximos 7 días.** Frase simple, lista con el rango **anclado** y el nivel de aviso con su
  explicación en lenguaje llano. Si el día es extrapolado, "por encima del rango calibrado".
- **T2 — Gráfico principal legible.** Ejes con valores y unidades, eje X con fechas en español,
  umbrales etiquetados sobre la línea, pronóstico como banda, tooltip al tocar con fecha y valor, y
  leyenda propia. Se elimina la leyenda por defecto de uPlot.
- **T3 — Historial completo** (desde el primer dato disponible hasta hoy) con los eventos marcados:
  may 2024 (9,06 m), jun 2025 (~7,6 m) y jul 2026, y los días en alerta sombreados.
- **T4 — "¿Cuánto acierta el pronóstico?"**: pronóstico a 3 días que se hizo en su momento vs lo que
  pasó, con el error promedio en una frase ("En promedio se equivoca ±X,X m").
- **T5 — Aguas arriba** (`/pronostico/aguas-arriba`): tendencia de lo que viene por el río,
  explicada ("lo que pasa allá llega a Colón después").
- **T6 — Contexto**: "Hoy el río está más alto que el X % de los días del año", y hoy vs la misma
  fecha de años anteriores.
- **T7 — Superficie afectada**: curva de hectáreas inundadas según la altura (de `capas/index.json`),
  sincronizada con el slider del mapa.
- **T8 — Detalle técnico (colapsado)**: caudal en m³/s real y pronosticado, fecha de emisión de
  Google, fuentes y metodología.

### Mapa

- **M1** — Mínimo 60 % del alto de la pantalla en mobile; columna completa en escritorio.
- **M2** — Controles fuera del mapa, o en un panel inferior plegable que no tape la ciudad. Los
  botones de escenarios no se cortan (scroll horizontal con indicador, o chips que envuelven).
- **M3** — Arranca en la altura pronosticada máxima **anclada**, con leyenda de profundidad y el
  texto "Si el río llega a X m, estas zonas podrían inundarse".

## Fuera de alcance

- No se cambian umbrales, curva caudal→altura, cero del hidrómetro ni los textos de riesgo oficiales
  (CLAUDE.md §5 y §9). El anclaje es una capa de presentación **sobre** la curva, no una recalibración.
- No se toca el cálculo del nivel de aviso: sigue siendo por **caudal** a 3 días (§5). El anclaje
  afecta alturas mostradas, nunca el aviso.
- No se agregan frameworks, trackers ni servicios pagos.
- No se corrige la latencia de 17 h del dato del INA (problema 4): es del worker, no de la UI. Se
  muestra con su antigüedad, como hoy. Queda anotado para una spec de worker.
- No se rehace el geoprocesamiento ni se regeneran capas.

## Diseño / decisiones

### Anclaje del pronóstico (C2)

En `backend/app/config/dominio.py`, documentado como técnica de presentación:

```
sesgo_m   = altura_real_actual_m − altura_est_m(día con fecha == hoy)
factor(n) = max(0, 1 − n / HORIZONTE_ANCLAJE_DIAS)     # n = días desde hoy, 0 = hoy
altura_anclada = altura_est_m + sesgo_m · factor(n)
```

- `HORIZONTE_ANCLAJE_DIAS = 7`: el sesgo decae linealmente hasta 0 en el día 7.
- Se aplica a `altura_est_m`, `altura_min_m` y `altura_max_m` por igual (traslada la banda, no la
  ensancha).
- **No** modifica `caudal_m3s` ni el aviso.
- Si no hay día con `fecha == hoy`, o no hay altura real, **no se ancla** y se informa.

**Contrato (aditivo, no rompe a la 005):** `DiaPronostico` suma `altura_anclada_m`,
`altura_anclada_min_m`, `altura_anclada_max_m`. `Pronostico` suma:

```
anclaje: { aplicado: bool, sesgo_m: float | null, altura_real_m: float | null,
           fecha_referencia: date | null, motivo: str | null }
```

En la UI, todo rango anclado lleva el texto "ajustado a la altura real de hoy", con una explicación
accesible de una frase. El rango se sigue mostrando **siempre como rango** (§5, §9).

### Endpoint nuevo `/api/estadisticas`

```
GET /estadisticas → {
  percentil_hoy: { altura_m, percentil, ventana_dias },
  error_pronostico: { lead_dias: 3, muestras: int, mae_m: float | null },
  dias_en_alerta: [ { desde: date, hasta: date, max_m: float } ],
  mismo_dia_otros_anios: [ { anio: int, altura_m: float } ],
  eventos: [ { fecha: date, altura_m: float, etiqueta: str } ]
}
```

Se calcula sobre lo que ya está en la base (alturas + pronósticos). Sin llamadas externas en el
request path (§3). Contrato en `contracts/openapi.yaml` y tests en `backend/tests/`.

### Librería de gráficos: se mantiene uPlot

El pedido permite cambiar a Chart.js. **No se cambia**, y la razón es el usuario: uPlot pesa ~47 KB
gzip contra ~200 KB de Chart.js, y esta app se diseña para 360 px y 3G (CLAUDE.md §7). Todos los
problemas de legibilidad listados —ejes, fechas en español, umbrales etiquetados, banda, tooltip,
leyenda propia— se resuelven configurando uPlot y escribiendo la leyenda a mano; ninguno requiere
otra librería. Si durante la implementación aparece un problema de legibilidad que uPlot no pueda
resolver, se documenta acá antes de cambiar.

### Estructura del frontend

- Se respeta el patrón existente `derive*View(data) + render*(el, view)`: lógica pura testeable,
  DOM aparte. Los gráficos nuevos exponen su serie construida como función pura testeable.
- Layout responsive real: una columna en mobile, grilla de dos columnas desde 900 px con el mapa
  ocupando la columna completa.
- Jerarquía de lectura: estado de hoy y qué hacer arriba; gráficos de contexto después; detalle
  técnico colapsado al final.
